0. Programs as Systems — The Four Questions

Every program you have written stores some information and changes it. That is the seed of a bigger idea: a program is a system — something with a current condition, events that alter that condition, influences that arrive from outside, and rules that must hold throughout. Thinking of a program as a system gives you a way to reason about what it is doing at any moment, what it is allowed to do next, and whether it is behaving correctly.

The ISTI model names the four properties every system has:

State what the system remembers right now Inputs what can arrive from outside and trigger a change Transitions what events change the state, and how Invariants what must remain true through every change

These four questions work at two distinct levels, and keeping those levels separate is the central skill this workbook develops.

The problem level and the program level

At the problem level, ISTI describes the real-world situation — before any code exists. The state of a campus meal-plan account is the student's balance. A transition is the event "student swipes at the dining hall." An invariant is "the balance is never negative." None of this mentions Python.

At the program level, ISTI describes what the code actually does. The state is a data structure — a dict, a list of records, a number. Transitions become Python functions. Invariants become checks you can run. And the program introduces additional data that exists purely to help the code do its work — loop counters, flags, accumulators — that have no counterpart in the problem world. These are called program artifacts. They are part of the program state — the computer is tracking them — but they are not part of the problem state, because they represent nothing in the real world.

The distinction matters because this is where bugs live. A program can be syntactically correct and still misrepresent the problem world — because it can express states the world can never be in, or fail to express states it legitimately can. Every section in this workbook asks both: what does the problem require, and what does the program actually do?

⚡ The Gap Between Levels Is Where Bugs Are Born

Problem-level thinking tells you what should be true. Program-level thinking tells you what the code actually does. When those diverge — when the program can represent something the world can't, or vice versa — you have a modeling error no amount of clean syntax can fix. The tools this workbook gives you are for finding and closing that gap.

Solve it before you code it

There is one more step that happens before even the problem-level ISTI analysis — and it is the step most students skip. Before you think about state, before you think about transitions, you must first solve the problem in your head using a concrete example.

This is not optional. A student who cannot trace through a specific example by hand — "I have $30 on my card, I try to buy a $28 meal, what happens?" — is not ready to design a data structure or write a function. They will code their confusion into the program and debug it for hours.

The Before-You-Code check is three steps, done before touching a keyboard:

  1. State the problem in one sentence. Not the solution — the problem. "A student wants to pay for a meal using their dining card balance."
  2. Trace one concrete example by hand with specific numbers. Pick real values. Follow them through manually. "Balance is $30. Meal costs $28. After the swipe, balance is $2."
  3. State the answer out loud. Not in code. In plain English. "If the balance is enough, subtract the meal cost from the balance. If not, decline and change nothing."

Only after you can do all three are you ready to think about data structures, transitions, and invariants. The ISTI analysis is not a substitute for this step — it is the formalization of it.

1. State — What the System Remembers ⚡ KEY IDEA

Defining state

Problem state is the collection of data structures needed to represent the problem before a transition executes. Note two things about this definition. First, it says "data structures" broadly — a single number like a balance is a data structure just as much as a dict or a list. Second, it says "before a transition executes" — state is what you have to work with before anything happens. Transitions operate on state; they don't define it.

Program state is everything the computer is tracking at a given moment — the problem state plus program artifacts like loop counters, flags, and accumulators. When you are reasoning about whether your system correctly models the world, focus on the problem state. When you are debugging a computation, you may need to inspect the full program state including artifacts. Recognizing the difference between problem state and program state keeps your mental model clean.

State is a choice, not a given

The world does not hand you a list of what to store — your questions do. Before designing any state, ask: what questions must this system be able to answer? That list determines the state.

Consider a traffic light. If the only question is "which light is currently on?", the state is just the current color. But if the question is also "how long has this light been green?", you need a timer. If the question is "how many vehicles passed through on green today?", you need a counter. Same physical system, different questions, different state.

Representation is a design decision

Once you know what question you are answering, you still have to choose how to represent the answer — and different representations have different consequences.

Consider the traffic light state. The simplest representation stores just the current color as a string:

traffic_light = {'color': 'red'}

An alternative representation uses a boolean for each color:

traffic_light = {'red': True, 'yellow': False, 'green': False}

Both answer the question "which light is on?" But they create very different obligations. With the string representation, it is impossible for two lights to be on simultaneously — the structure prevents it. With the boolean dict, the value {'red': True, 'yellow': True, 'green': False} is a perfectly valid Python object, but it represents something that can never exist in the real world. You have now taken on the obligation to enforce — through logic in your code — that exactly one value is True at all times.

This is the central lesson of representation: every representation choice creates a different set of rules you must maintain. The string representation makes the illegal state impossible to express. The boolean dict is more flexible but trades that safety for additional enforcement work. Neither is simply "better" — the right choice depends on your context. But the decision must be made consciously, not accidentally.

Stored state vs. derived state

Once you know what the system must answer, a second question arises: does the answer need to be stored, or can it be computed from what is already stored?

Derived state is information that can be computed from the primary state at any time. A meal-plan account's primary state is the balance. "Is this account low?" is not separate state — it is a derived fact, computed by comparing the balance to a threshold. A gradebook's primary state is the list of scores. The average is derived: sum(scores) / len(scores).

Be thoughtful about storing derived state. If you store a derived value, you take on an additional rule: the stored value must always equal what the computation would produce. Every time the primary state changes, you have to update the derived value — and if you forget once, you have silent wrong data. Computing on demand enforces the rule automatically.

# Primary state — store this
account = {"balance": 450.00, "transactions": [...]}

# Derived — compute on demand, don't store
def is_low(account, threshold=20.00):
    return account["balance"] < threshold

def total_spent(account):
    return sum(t["amount"] for t in account["transactions"]
               if t["type"] == "swipe")

# Be careful with this — now you must keep spent_total in sync manually:
# account = {"balance": 450.00, "transactions": [...], "spent_total": 230.00}

That said, there are cases where storing a derived value is the right call. If computing it is very expensive and the question is asked constantly, storing it may be worth the maintenance cost. And if a value depends on information that will no longer be available later — "what was the balance at close of business yesterday?" — it had to be stored at the time, because it cannot be reconstructed from today's state.

When a new question changes everything — the counter vs. log decision

One of the most important lessons about state is that adding a new question can force a completely different representation. This is not a refinement — it is a redesign.

Suppose the only question your meal-plan system must answer is "how many transactions occurred today?" A single integer counter is the right design:

account = {"balance": 450.00, "transaction_count": 0}

def swipe(account, amount):
    account["balance"] -= amount
    account["transaction_count"] += 1

The counter is primary state — it cannot be derived from anything else you are storing. It is also not "history" in any meaningful sense; it is just a running total. This is the simplest solution to the question asked.

Now add a second question: "show me the transactions from this morning." Suddenly the counter is useless. You cannot reconstruct the individual transactions from a count. The representation must change entirely — you now need a log:

account = {"balance": 450.00, "log": []}

def swipe(account, amount, location):
    account["balance"] -= amount
    account["log"].append({
        "type": "swipe", "amount": amount,
        "location": location, "balance_after": account["balance"]
    })

And once you have the log, the count becomes derived — you compute it from the log rather than maintaining a separate counter that could get out of sync:

def transaction_count_today(account):
    today = get_today()   # e.g., datetime.date.today()
    return sum(1 for t in account["log"] if t["date"] == today)

The full cascade: if the only question is a count, store a counter. If you need details about individual transactions, store a log. If you have the log, derive the count from it. The choice of representation flows entirely from the questions the system must answer — and a new question can force you back to the beginning.

History as state

The current state of most systems tells you nothing about how it got there — the current balance does not reveal which transactions produced it. If the system must answer questions about the past, past transitions must be preserved as state. They are not derivable from the current snapshot. When a transition happens, append a record of it to a log. The log is then part of the state, not a convenience — losing it means those questions become unanswerable.

The two-way test

Once you have chosen a representation, run it in both directions. World → program: can every meaningful real-world state be expressed? A meal-plan account with exactly zero balance is valid — can your representation express it? An account that has never been used? One with a very long transaction log? Program → world: does every state your program can express correspond to something meaningful in the world? A negative balance, if the account forbids overdraft, is a program state with no real-world meaning. Two log entries for the same transaction is similarly nonsensical.

Every mismatch in either direction is a future bug, discoverable today for free. Run this test every time you choose a representation.

⚡ Key Idea — State is Chosen, Not Found

The world does not hand you a list of what to remember. Your questions do. Decide what the system must be able to answer, then choose the representation that makes those answers easy and makes invalid conditions impossible — or at least explicitly enforced.

Be thoughtful about storing derived state — prefer computing it, but recognize there are cases where storing it is the right call. And distinguish carefully between problem state, which represents the real world, and program state, which includes everything the computer is tracking — among them program artifacts that have no real-world meaning.

🤖 When You Direct an AI

The data structure you specify in a prompt is the state. An AI given "track a meal-plan account" will invent its own representation. An AI given "the account is a dict with keys balance (float) and log (list of transaction dicts)" builds exactly what you designed. The most important sentence in any prompt about a system is the one that names the state's shape. Everything else follows from it.

2. Inputs — What Arrives from Outside

What makes something an input

A system doesn't change on its own. Something from outside triggers a change. Inputs are those triggers — events or data that arrive from actors who don't know your rules, may make mistakes, and arrive at unpredictable times.

At the problem level, inputs are real-world events: a student swipes a card, a librarian checks in a book, a teacher enters a grade, a coin is inserted into a vending machine. Each event carries data — the swipe amount, the book's ID, the score, the coin denomination — and the system must respond to it.

Three things distinguish inputs from the state changes they cause. First, inputs are external — they come from actors outside the system. Second, they are not under your control — the student might swipe with an empty balance, the librarian might scan an unknown barcode, the teacher might enter a negative score. Third, they are the trigger for a transition, not the transition itself. The input arrives; then the system decides what to do with it.

Preserve your inputs

As a matter of good practice, always preserve your inputs as part of the initial state before doing anything else with them. This creates an audit trail — if something goes wrong during processing, you can always go back and see exactly what arrived, before any code touched it. It also separates two things that are easy to conflate: receiving an input and acting on it. Preserving the raw input makes that separation concrete.

def initialize_account(student_id, opening_balance):
    # Preserve the inputs as part of the initial state
    account = {
        "student_id": student_id,
        "opening_balance": opening_balance,   # preserved — never changes
        "balance": opening_balance,           # working copy — transitions modify this
        "log": []
    }
    return account

In this course, store preserved inputs as part of the initial state. In larger production systems you would often separate raw input records from operational state, but the principle — preserve what arrived before you process it — remains the same.

The boundary: validate once, trust inside

Every system has a boundary: the edge between the interior (which you control) and the outside world (which you don't). The discipline that makes interior code simple is to validate everything at the boundary and trust it everywhere inside. If you validate inside every transition instead, you write the same checks repeatedly and eventually forget one.

# At the boundary: validate before anything enters
def read_positive_float(prompt):
    while True:
        try:
            amount = float(input(prompt))
            if amount > 0:
                return amount       # clean — let it through
        except ValueError:
            pass
        print("Please enter a positive number.")

# Interior transition: trusts that amount is valid
def deposit(account, amount):
    account["balance"] += amount
    account["log"].append({"type": "deposit", "amount": amount,
                           "balance_after": account["balance"]})

This pattern — validate at the door, trust inside — means every transition can be written cleanly without defensive checks cluttering its logic.

Three places the boundary appears

User input is the obvious one — typed values that can be wrong type, wrong sign, or empty. Handle with try/except and a validation loop.

Loaded files are a less obvious boundary crossing. When you reload a saved account from JSON, that file is an input. It could have been hand-edited, written by a buggy earlier version of your program, or simply corrupted. A loaded file is not trusted state — it is untrusted input that happens to look like state. Check it before using it. Section 4 will show you how.

Function arguments — at the function level, the parameter list is a boundary. If your function is called by other parts of your own program, its arguments are inputs to that function. Zoom in far enough and every function is a small system with its own inputs.

Outputs: projections, not mutations

The boundary runs in both directions. Outputs leave the system outward — a balance report printed to the screen, a summary saved to a file. The discipline for outputs is the mirror of input validation: outputs should be projections — read-only views of the state. A function that formats and prints the account balance should never modify it. A function that quietly adjusts the state on the way out is a transition wearing a disguise, and it is one of the hardest bugs to find because nobody looks for side effects in a reporting function.

def report(account):
    # read-only — this is a projection, not a transition
    print(f"Balance: ${account['balance']:.2f}")
    print(f"Transactions this session: {len(account['log'])}")
🤖 When You Direct an AI

When specifying a transition to an AI, always say explicitly what validation has already happened at the boundary. "Assume amount has already been validated as a positive float" tells the AI the function body should be clean. "Write the validation too" tells it to include the boundary check. Without this, the AI guesses — and may either add unwanted validation inside the function or omit it entirely.

3. Transitions — What Changes the State ⚡ KEY IDEA

What a transition is

A transition is an event that takes the system from one state to another. At the problem level, transitions are real-world events: a student swipes, a library book is returned, a grade is recorded, a vending machine dispenses an item. At the program level, each transition becomes a Python function — named for the event, with a body that says exactly which pieces of state it touches and how.

Two naming principles follow directly. Functions that are transitions should be named as events: swipe_card, return_book, enter_grade, dispense_item. And the function body should touch only the state that the event actually changes — a swipe affects the balance and the log, and nothing else.

Articulate the entire state space before writing any code

Before you write a single line of Python for a transition, you must articulate the entire state space: every configuration the system could be in when that transition fires. This is not optional. A transition that handles only one configuration is not written correctly — the cases it skips become bugs.

Think of designing transitions the way a contract lawyer thinks about contingencies. A contract that only specifies what happens when everything goes well is not a contract — it is a wish. A useful contract specifies what happens in every case. The same is true of a transition: you must specify its behavior for every state the system could be in when it fires.

For the vending machine's "dispense item" transition, articulate the state space first — in plain English, before any code:

dispense(machine, item_code) — state space:
  if item_code not in machine["catalog"]        → print("Unknown item."); return
  if machine["inventory"][item_code] == 0       → print("Sold out."); return
  if machine["credit"] < machine["prices"][item_code]
                                                → print("Insufficient credit."); return
  otherwise:
    machine["inventory"][item_code] -= 1
    machine["credit"] -= machine["prices"][item_code]
    # dispense the item

Notice that all three denial paths leave the state completely unchanged. This is a deliberate design decision — a denied transition changes nothing. State it explicitly so there is no ambiguity about what "deny" means for the state.

Notice also the defensive pattern on the final branch. If your state space analysis is correct, you should never reach an unexpected condition. But if you somehow do, make it loud:

def process_status(account):
    if account["status"] == "active":
        # handle active account
        pass
    elif account["status"] == "suspended":
        # handle suspended account
        pass
    else:
        print(f"FATAL ERROR: unexpected account status '{account['status']}': 301")
        exit()

The number (301) acts as a unique error code — if this ever fires in testing, you know exactly which branch in which function to inspect. This is a sign that your state space analysis missed a case, and the program is telling you loudly rather than silently producing wrong results.

Drawing the state space

For small systems, drawing the state space — every valid state as a node, every transition as a labeled arrow — makes the completeness requirement visible. For the traffic light:

change change change [ green ] ─────────► [ yellow ] ─────────► [ red ] ─────────► [ green ]

Every state has an outgoing arrow. There are no dead ends. Every transition is defined for every state it can be called from. This is a complete state machine.

For richer systems the full diagram is too large to draw, but the discipline of asking "what is every state this transition could be called from?" is always applicable, even when the diagram is not.

The second-call test and order sensitivity

Two questions to ask of every transition you write. The second-call test: what happens when this transition fires again immediately after it just fired? Depositing twice should add twice — that is the desired behavior. Checking out a book that is already checked out should be denied — that is also desired behavior. But "desired" is a decision you must make explicitly, not discover accidentally.

Order sensitivity: does the final state depend on the order in which transitions fire? For a meal-plan account: swipe-then-deposit may be denied (balance too low after the swipe), while deposit-then-swipe succeeds. That is correct behavior for a real system — orders are processed in the order they arrive. But it must be a deliberate decision, not a surprise.

# Two trajectories, same actions, different order
# Starting state: balance = 10.00

# Trajectory A: deposit first
deposit(account, 20.00)     # balance → 30.00
swipe_card(account, 25.00)  # balance → 5.00  ✓ succeeds

# Trajectory B: swipe first
swipe_card(account, 25.00)  # balance would go to -15.00 → DENIED
deposit(account, 20.00)     # balance → 30.00

# Same actions, different order, different final states
# This is correct behavior — not a bug

Program artifacts in transitions

At the program level, transition functions introduce artifacts alongside the state changes. An early return after a denial is a control-flow artifact. An intermediate variable cost = shares * price is a computational artifact. The variable sym in a loop over positions is an iteration artifact. These are part of the program state while the function runs — the computer is tracking them — but they have no problem-level counterpart. They are not part of the problem state.

def swipe_card(account, amount):
    # Guard: deny if swipe would exceed balance
    if amount > account["balance"]:
        print(f"Denied: insufficient balance (${account['balance']:.2f})")
        return                  # program artifact: early return (control flow)

    new_balance = account["balance"] - amount   # program artifact: intermediate value
    account["balance"] = new_balance
    account["log"].append({
        "type": "swipe",
        "amount": amount,
        "balance_after": new_balance   # stored — needed for audit questions
    })
⚡ Key Idea — Articulate the Entire State Space

A transition is not written correctly until it specifies its behavior for every state the system could be in when it fires. The happy path is one case; the denial cases, the edge cases, the repeated call, the out-of-order call — those are the rest. The ones you skip are the bugs you debug later.

Do this work before writing Python. Write the cases in plain English first. Then translate each case into code. The defensive else with a FATAL ERROR message is your safety net for cases you believed were impossible — if one ever fires, the program tells you loudly that your analysis was incomplete.

🤖 When You Direct an AI

When you ask an AI to write a transition, the most important thing you can specify is every case it must handle — not just the success path. "If the swipe amount exceeds the balance, print a denial message and return without changing anything" eliminates an entire class of bug. An AI given only the success case will implement only the success case.

4. Invariants — What Must Always Stay True ⚡ KEY IDEA

What an invariant is

An invariant is a condition that must hold in every state the system is ever in — not just after the happy-path transition, but after every transition, from every starting state, including the ones you haven't tested yet. An invariant that holds most of the time is not an invariant; it is a bug waiting for the right combination of inputs.

Invariants come from two sources. Domain invariants are rules of the problem world, true before any code exists. "A meal-plan balance is never negative" is a rule of the account type, not a programmer's choice. "A library book cannot be checked out to two patrons simultaneously" is a physical fact. "A gradebook score is between 0 and 100" is a rule of the grading system. These are discovered by asking the domain expert: what must never happen?

Structural invariants are rules about the data structure itself, arising from design choices. "Every transaction in the log has a 'type', 'amount', and 'balance_after' key." "The log is in chronological order." "Every inventory count is a non-negative integer." These are not facts about the world — they are commitments you made when you chose the representation, and breaking them means the code that reads the structure will behave unpredictably.

Meal-plan accountBalance ≥ 0; every transaction has a positive amountLog entries have required keys; log is in order of occurrence

Three ways invariants are enforced

Not all invariants require the same kind of enforcement. There are three modes, and choosing the right one for each rule matters.

1. Structural enforcement — the strongest kind. The data structure itself makes the illegal state impossible to express. A dict keyed by book ID cannot have two entries for the same book; the invariant "a book has at most one checkout record" is guaranteed by the shape. You get this enforcement everywhere, automatically, including in code that hasn't been written yet. When you can choose a representation that makes an illegal state impossible to express, always prefer it over enforcing the rule in code.

2. Logic enforcement — for invariants the structure cannot enforce on its own. An if check inside every relevant transition verifies that the rule holds before or after the state change. This is the same if your transitions already use for denial cases — the tool is familiar, the application is new.

def check_invariants(account):
    if account["balance"] < 0:
        print(f"INVARIANT VIOLATED: balance is negative ({account['balance']})")
        exit()
    if not isinstance(account["balance"], (int, float)):
        print(f"INVARIANT VIOLATED: balance is wrong type ({type(account['balance'])})")
        exit()
    for i, t in enumerate(account["log"]):
        if "type" not in t:
            print(f"INVARIANT VIOLATED: log entry {i} missing 'type'")
            exit()
        if "amount" not in t:
            print(f"INVARIANT VIOLATED: log entry {i} missing 'amount'")
            exit()
        if t["amount"] <= 0:
            print(f"INVARIANT VIOLATED: log entry {i} has non-positive amount")
            exit()

Collect all of a system's invariants into one check_invariants function and call it after every transition and after every load from disk. With this discipline in place, a bug cannot hide "somewhere" — the first failing check pins it between two checkpoints. The state was valid, one transition ran, the state is now invalid: that transition is the suspect.

check_invariants(account)         # passes — state is valid
deposit(account, 20.00)
check_invariants(account)         # passes

swipe_card(account, 15.00)
check_invariants(account)         # INVARIANT VIOLATED: balance is negative
                                  # — the culprit is swipe_card

3. Defensive else — for transitions where one branch should be unreachable given your state space analysis. As shown in Section 3, if the program reaches that branch anyway, it should stop loudly and tell you exactly where. This is not an invariant check in the traditional sense — it is a signal that your analysis was incomplete.

Guards vs. invariant checks: an important distinction

Not every check is an invariant enforcement. Some checks are guards — polite refusals of requests the outside world is legitimately allowed to make. A student asking to swipe more than their balance is not a bug. It is a normal, expected input that the system must handle gracefully. An if guard handles it with a message and a clean return.

An invariant check — whether structural or logic-enforced — is reserved for conditions that must be impossible if the code is correct. If the balance goes negative after a transition, that is not a user error — it is a bug in the transition.

SituationCorrect toolWhy
Swipe amount exceeds balanceif guard + message + returnNormal input — users run out of money
Balance is negative after a swipeInvariant check in check_invariantsShould be impossible if the guard works — this is a code bug
Log entry missing a required keyInvariant check in check_invariantsThe code that creates log entries should always include them

A failing guard means "the world sent a valid but inconvenient request — handled." A failing invariant check means "the code has a bug — stop and fix it." Confusing the two either causes crashes on valid inputs or lets bugs propagate silently.

Invariants catch loaded-file corruption

Recall from Section 2 that a loaded JSON file is an input, not trusted state. Calling check_invariants immediately after loading turns silent corruption into a loud, located failure at the boundary — before it can propagate through the rest of the program.

with open("account.json") as f:
    account = json.load(f)
check_invariants(account)   # fail here, loudly, if the file is wrong
                            # not 200 lines later in a confusing cascade
⚡ Key Idea — An Invariant You Can Run Is a Tripwire

When an invariant lives only in comments or design notes, it can be violated silently and the violation can travel far before anyone notices. When it is a check called after every transition, it fires the moment the rule breaks and names exactly which transition broke it.

Write the rules in plain English first. Then ask: is this rule enforced by the structure (best), enforced by logic in check_invariants (good), or does it require a defensive else to catch the impossible (safety net)? Match the enforcement to the kind of rule.

Compare what it proposes against your own list; anything it finds that you missed is a gap in your specification. The AI should ask you how you want to handle each gap — not decide for you.

5. ISTI as Specification — Directing the AI ⚡ KEY IDEA

Workbook 1 described three ways to use AI. The third — and the only one that keeps the design yours — is: you do the design thinking, the AI executes and interrogates. Everything in this workbook has been building toward that. A complete ISTI description is a complete design. The prompt is how you hand that design to the AI.

The AI as Socratic partner, not answer machine

Before looking at the worked example, you need to understand how to use the AI in this process — because it is probably different from how you have used it before.

Most students use AI the same way: ask a question, receive an answer, copy the answer. That mode of use does not develop skill. If the AI builds the system for you, the design still belongs to whoever wrote the prompt — and if that wasn't you, you learned nothing.

In this process, the AI plays a different role. When it finds a gap in your specification, it does not fill the gap — it asks you how you want to handle it. When your proposed solution has a problem, the AI explains what is wrong with your reasoning, not what the right answer is. Only if you are truly stuck does the AI offer frameworks for thinking — ways of approaching the problem, not the answer itself.

This means you should expect the AI to push back. That is not a failure — it is the AI doing its job. When it asks "how do you want to handle the case where the deposit amount is less than the fee?", it has found a real gap in your design. The answer is yours to work out.

A well-written ISTI spec also happens to be AI-agnostic — you can give it to Claude, ChatGPT, or any other tool and get consistent, comparable results, because the design is fully specified before the AI touches it. The AI becomes interchangeable. The quality of the code the AI produces is a direct reflection of the quality of your spec — and students feel that immediately. A vague spec produces vague code. A precise spec produces precise code.

The three-step workflow: Problem → Program → Prompt

The workflow maps directly onto the two-level framework this workbook has been building. Each step is distinct. The design happens entirely before the AI is involved.

Step 1 — Problem level (ISTI spec in plain English). Describe the system in the language of the real world, with no Python. What must be remembered? What events happen? What rules hold? This is the problem state description. Nothing here mentions data structures or implementation.

Step 2 — Program level (pseudocode). Cross from the problem world into the implementation world. Write four to six lines that commit to the order of operations. This is where you make the implementation decisions: check the guard before changing anything, compute the new balance, update the state, record the transaction. If you can write these lines, the Python is a translation exercise.

Step 3 — The prompt. The prompt formalizes the pseudocode as instructions for the AI. It adds no new thinking — it writes down what the pseudocode already decided, in enough detail that the AI has nothing left to guess.

A worked example: swipe_card

Step 1 — Problem-level ISTI spec:

SYSTEM     Campus meal-plan account

STATE      The account has a current balance (a dollar amount, never negative)
           and a log of every transaction that has occurred.

INPUT      A swipe event: the cost of the meal being purchased (a positive
           dollar amount, already validated before this function is called).

TRANSITION swipe_card — the student uses their card to pay for a meal.
  Cases:
    If the meal cost exceeds the current balance:
      → the card is declined; nothing changes
    Otherwise:
      → the balance decreases by the meal cost
      → a record of the transaction is added to the log

INVARIANTS after the call:
    The balance is never negative.
    Every log entry records the type, amount, and balance after the transaction.

Step 2 — Program-level pseudocode:

check whether amount exceeds balance — if so, print denial message and return
compute new_balance = balance - amount
update account["balance"] to new_balance
append {"type": "swipe", "amount": amount, "balance_after": new_balance} to log

Four lines. The first line encodes a critical decision: check before changing anything, so a declined swipe leaves the account exactly as it was. This is the order-of-operations decision that must be made explicitly — it cannot be left for the AI to guess.

Step 3 — The prompt:

"The account state is a dict with two keys: 'balance' (float, never
 negative) and 'log' (list of dicts). Each log entry has keys 'type'
 (str), 'amount' (float, positive), and 'balance_after' (float).

 Write swipe_card(account, amount). Assume amount has already been
 validated as a positive float before this function is called.

 If amount exceeds account['balance']: print a denial message and
 return immediately — do not change anything.
 Otherwise: subtract amount from balance and append
 {'type': 'swipe', 'amount': amount, 'balance_after': new_balance}
 to log. Return None. Print nothing on success.

 Use only basic Python: dicts, lists, functions, no imports."

Read the prompt against the pseudocode: every line of the pseudocode is present. The AI has nothing left to design — no structure to guess, no edge case to invent, no order of operations to decide.

Using the AI to find gaps — deliberately

After receiving the code, ask the AI one more question:

"What cases or edge conditions does my specification not address?
 Don't fix them — ask me how I want to handle each one."

For swipe_card as specified, a good AI might ask: "Your spec doesn't say what happens if amount is exactly equal to balance — is that a successful swipe that results in a zero balance, or should it be treated differently?"

This is a real question. Zero balance is a valid state for a meal plan card — the student has spent everything. So the answer is: a swipe for exactly the balance amount succeeds, leaving a zero balance. You add that to the spec and the AI updates the code.

The AI found the gap. You decided how to handle it. The design is still yours.

If you propose a solution the AI thinks has a problem — say, you decide that a zero balance should be denied — the AI might respond: "If you deny a swipe when balance equals amount, the student can never spend their last dollar. Is that the intended behavior for this account type?" It explains what is wrong with your reasoning. It does not tell you what to do instead. You have to think it through.

The test of a complete specification

One question tells you whether a specification is complete: could two different people, given only this description, build interchangeable implementations? If not, something is unspecified — a case that isn't covered, a data structure field that isn't named, a rule that isn't stated. Find it and add it before sending the prompt.

⚡ Key Idea — The Prompt Documents the Design; It Does Not Make It

The prompt is the output of your thinking, not the start of it. The workflow is: solve the problem in your head first (Before-You-Code), write the problem-level ISTI spec, write the pseudocode, then formalize it as a prompt. Anyone can copy a finished prompt and receive correct code — but the design belongs to whoever worked through those three steps.

Use the AI to interrogate your design — not to make it. When the AI finds a gap, that is a success. It means your spec was good enough to expose the question. Answer the question, update the spec, and continue.

7. Glossary

ISTI vocabulary. Terms from Workbooks 2 and 3 (list, dict, function, key function, accumulator, aliasing, mutability, representation) are defined in those glossaries.

B – D

Before-You-Code
The three-step check required before any design or coding work: (1) state the problem in one sentence; (2) trace a concrete example by hand with specific values; (3) state the answer in plain English. Skipping this step means coding your confusion. Section 0.
boundary
The edge of a system: inside it you control everything; outside it nothing. Inputs cross inward (validate them), outputs cross outward (project, don't mutate), state crosses time through files (check on the way back in). Section 2.
derived state
Information that can be computed from the primary state at any time. Be thoughtful about storing it — storing a derived value creates a synchronization rule you must maintain manually. Example: average score is sum(scores) / len(scores). Section 1.
domain invariant
A rule that comes from the problem world, not from the code: "balance is never negative," "a book cannot be checked out to two patrons." Discovered by asking "what must never happen?" Section 4.

G – I

guard
An if-check that politely refuses a request the outside world is legitimately allowed to make (a swipe that exceeds the balance). Contrast with an invariant check, which halts on a condition the code itself must never produce. Section 4.
input
Anything that arrives from outside the system: typed values, loaded files, function arguments. Not trusted; preserved and validated at the boundary before entering the system. Section 2.
invariant
A rule that must hold in every state the system can be in, through every transition. Enforced structurally (by representation choice), logically (by if checks in check_invariants), or defensively (by else branches that should never fire). Section 4.
ISTI
Inputs, State, Transitions, Invariants — the four questions that describe any system, and the specification language this workbook is built around.

P – R

primary state
The information that must be stored because it cannot be derived from other stored values and cannot be reconstructed once discarded. Contrast with derived state. Section 1.
problem state
The collection of data structures needed to represent the real-world problem before a transition executes. Does not include program artifacts. Contrast with program state. Section 0.
program artifacts
Variables that exist to help the program run but have no counterpart in the problem world: loop counters, index variables, boolean flags, temporary accumulators. Part of the program state, but not part of the problem state. Section 0.
program state
Everything the computer is tracking at a given moment — the problem state plus program artifacts. When debugging a computation, you may need to inspect the full program state. Contrast with problem state. Section 0.
projection
A read-only view of state formatted for output — a report, a display. Projections never mutate state; a function that reads and writes state is a transition, not a projection. Section 2.

S – U

second-call test
Ask of every transition: what happens when it fires again immediately? Decide on purpose. Do not discover the behavior accidentally when a user does the same thing twice. Section 3.
state
What the system must remember in order to answer its questions. A choice, not a given — determined entirely by what the system must be able to say. See also: problem state, program state. Section 1.
state space
Every configuration the system could possibly be in. Transitions must be written correctly for every state in the space — not just the easy ones. Section 3.
structural invariant
A rule about the data structure itself arising from design choices: "every log entry has 'type', 'amount', and 'balance_after' keys." Contrast with domain invariant. Section 4.
transition
An event that takes the system from one state to another. At the problem level: a real-world event. At the program level: a function named for that event, whose body specifies the effect on state for every case in the state space. Section 3.
two-way test
The mapping audit run on every representation: (1) can every valid world-state be expressed? (2) does every expressible program-state mean something in the world? Both directions, every time. Section 1.
unrepresentable
The strongest form of invariant enforcement: choosing a data structure in which the illegal state cannot be expressed at all. Better than checking for the rule; the structure enforces it everywhere, forever. Section 4.
