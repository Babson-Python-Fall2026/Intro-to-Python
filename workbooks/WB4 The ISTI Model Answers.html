Section 1 — State

Question 1

A library checkout system must answer "which books does patron 1042 currently have?" and "is this book currently available?" What must the state include? What is derived?

Answer

The two questions drive the state design. "Which books does patron 1042 have?" requires a mapping from patron IDs to the books they hold. "Is this book available?" requires knowing which books are currently checked out. A single dict mapping book ID to patron ID answers both:

checkout = {"978-0-06-112008-4": "patron_1042",
            "978-0-14-028329-7": "patron_0887"}

From this structure, "which books does patron 1042 have?" is derived — iterate over the dict and collect entries whose value is "patron_1042". "Is book X available?" is also derived — check whether the book's ID is a key in the dict. Neither needs separate storage because both can be computed from the same structure on demand.

The catalog (the full list of books the library owns) is also primary state if the system must answer "does this book exist at all?" — without it, you cannot distinguish "not checked out" from "doesn't exist."

Question 2

A gradebook stores each student's list of quiz scores. A classmate proposes also storing the running average per student. Make the case for and against storing it.

Answer

Against storing it: the average is derived — sum(scores) / len(scores) computes it from the list at any time. Storing it creates a synchronization rule: the stored average must always equal what the formula would produce. Every time a score is added, the stored average must be updated. If a score is corrected and the average is not, you have silent wrong data that will be trusted because it looks like a real value.

For storing it: if the gradebook has thousands of students and the average is displayed on every page load, recomputing it every time may be slow enough to matter. Storing it trades maintenance cost for performance. This is a reasonable tradeoff only if the performance problem is real — not hypothetical.

Conclusion for this course: compute it. The gradebook is small, the computation is trivial, and storing it creates a rule you will eventually break. The case for storing it requires evidence of a real performance problem first.

Question 3

A vending machine must answer "how many items were sold today?" What is the simplest representation that answers only that question? Now add the question "which items were sold, and at what times?" How does the representation change? Once you have the new representation, is the count still primary state or is it now derived?

Answer

For count only: a single integer is the simplest correct design.

machine = {"credit": 0.00, "inventory": {...}, "sales_today": 0}

sales_today is primary state — it cannot be derived from anything else currently stored. Each dispense increments it by one.

Adding "which items, at what times?": the integer becomes useless. You cannot reconstruct individual transactions from a count. The representation must change to a log:

machine = {"credit": 0.00, "inventory": {...},
           "sales_log": [
               {"item": "B2", "price": 1.50, "time": "10:14"},
               {"item": "A1", "price": 0.75, "time": "11:02"}
           ]}

Is the count now derived? Yes. Once the log exists, len(machine["sales_log"]) gives the count. Maintaining a separate sales_today integer alongside the log creates a synchronization rule — they could get out of step. Compute the count from the log instead.

This illustrates the key lesson: a new question can force a completely different representation, and with it, a previously primary value becomes derived.

Question 4

The traffic light boolean dict {'red': True, 'yellow': False, 'green': False} — what rule does it fail to enforce that the string representation enforces automatically? How would you enforce that rule using logic in your code?

Answer

The string representation {'color': 'red'} makes it impossible for two lights to be on simultaneously — there is only one value, so only one color can be current. The boolean dict does not enforce this: {'red': True, 'yellow': True, 'green': False} is a valid Python dict that represents a physically impossible state.

To enforce "exactly one True" with logic, check it in check_invariants and in any transition that changes the light:

def check_invariants(light):
    active = sum(1 for color in ["red", "yellow", "green"] if light[color])
    if active != 1:
        print(f"INVARIANT VIOLATED: {active} lights are on simultaneously")
        exit()

def change(light, new_color):
    for color in ["red", "yellow", "green"]:
        light[color] = (color == new_color)   # set exactly one to True

The transition itself enforces the rule by design — setting the new color to True and all others to False in one operation makes it impossible to end up in a bad state, as long as change is the only way to modify the light.

Question 5

Run the two-way test on a gradebook that stores only each student's latest score. What valid world-state can it not express? What program-state can it express that means nothing in the world?

Answer

World → program (valid world-state it cannot express): a student who has taken three quizzes with scores 72, 85, and 91. The gradebook only stores 91 — the full history is gone. If the system ever needs to answer "show me this student's score trend" or "what was the score on quiz 2?", those questions become unanswerable. The current snapshot cannot represent a student with a meaningful score history.

Program → world (program-state that means nothing): a student in the gradebook dict with a score of -5, or a score of 150. Both are valid Python values, but neither corresponds to anything that can happen in the real grading system. The representation allows these values; the world does not.

A second world-to-program gap: a student who is enrolled but has not yet taken any quiz has a meaningful real-world state (enrolled, no scores yet). If the gradebook only stores students who have a score, this state is invisible to the program.

Question 2

Why is preserving inputs as part of the initial state a useful practice? Give a specific scenario where it helps.

Answer

Preserving inputs separates two things that are easy to conflate: receiving an input and acting on it. The preserved input is a record of exactly what arrived before any code touched it. If processing introduces a bug — say, a fee calculation is wrong — you can compare the preserved input against the processed state and see exactly where the values diverged.

Specific scenario: a student opens a new meal-plan account with a $500 deposit. The initialization code applies a $10 account-opening fee, so the working balance becomes $490. Three weeks later, the student disputes the opening balance, claiming they deposited $500. Without the preserved opening_balance field, there is no way to confirm what the original deposit was — the working balance of $490 could reflect a $500 deposit minus a fee, or a $490 deposit with no fee. With the preserved input, the answer is immediately available.

Question 3

Why is a loaded JSON file treated as an input rather than as trusted state? Give a specific example of how a saved file could be wrong.

Answer

A loaded file is treated as an input because it crosses the boundary — it came from outside the running program. The program cannot verify how it was produced. It could have been created by an older, buggy version of the program; it could have been hand-edited by someone who made a mistake; it could have been corrupted during saving or transmission. The fact that it looks like a dict does not make it trusted.

Specific example: a student's meal-plan account is saved to JSON with a balance of $45.00. Between sessions, someone opens the file in a text editor and changes "balance": 45.0 to "balance": -45.0 by accident while editing something nearby. When the program loads the file and trusts it without checking, it now has a negative balance — violating a fundamental invariant — and every subsequent swipe or deposit will produce wrong results. If check_invariants is called immediately after loading, this is caught at the boundary before a single transaction runs.

Question 4

The deposit function trusts that amount is valid. Where does that trust come from — and what happens to the system if that trust is misplaced?

Answer

The trust comes from the boundary validation that runs before deposit is called — specifically, read_positive_float(prompt), which rejects anything that is not a positive number. The contract is: the boundary does the checking; the interior trusts the result.

If that trust is misplaced — say, someone calls deposit(account, -50.00) directly from another part of the code, bypassing the validated input path — the function adds -50 to the balance, silently decreasing it. No error is raised, no message is printed. The balance is now wrong, and check_invariants may catch it on the next call — but the damage is already done and there is no record of what caused it.

This is why the boundary discipline matters: it only works if every path into the interior goes through the validation. A function that trusts its input is only as safe as the path that called it.

Question 5

What makes a function that modifies the state while printing a report harder to debug than a transition that explicitly modifies state?

Answer

When a function is named and structured like a report — print_summary(account) — nobody expects it to change anything. Debugging assumes that calling a reporting function is safe to do at any point, including inside a debugging session while inspecting state. If that function secretly modifies state, every call to inspect the state also changes it — making the bug move around or disappear when you look at it.

More concretely: if you are tracing a bug and you add a call to print_summary(account) to see what the state looks like at a certain point, and that function happens to apply a fee or update a counter, your debugging code has now changed the behavior of the program. The bug you were chasing is now different.

A transition named apply_monthly_fee(account) is inspected for state changes as a matter of course. A reporting function is not — which is exactly what makes hidden mutations in reporting functions so dangerous.

Section 3 — Transitions

Question 1

For the library checkout system: before writing any Python, write in plain English the complete state space for check_out(library, patron_id, book_id) — every case it must handle. Include the denial condition and response for each.

Answer

State space for check_out(library, patron_id, book_id):

  • Patron does not exist in the library system → print "Patron ID not found."; return; state unchanged.
  • Book does not exist in the catalog → print "Book not found in catalog."; return; state unchanged.
  • Book is already checked out → print "Book is currently checked out."; return; state unchanged.
  • Patron has reached their checkout limit → print "Patron has reached maximum checkout limit."; return; state unchanged.
  • All checks pass (normal case) → record the book as checked out to this patron; update the checkout record; state changes.
  • Defensive else → if somehow none of the above conditions matched and the normal case was not reached, print "FATAL ERROR: unexpected state in check_out: 401"; exit().

Every denial path leaves the state completely unchanged. The normal case is the last branch — it only executes after every denial condition has been ruled out.

Question 2

Apply the second-call test to swipe_card: what happens if you call it twice with the same amount? Is that the correct behavior?

Answer

If the balance is sufficient for both swipes, calling swipe_card(account, 10.00) twice deducts $10 each time, leaving the balance $20 lower and two entries in the log. This is correct behavior — a student who swipes twice has made two purchases, and the system should record and charge both.

If the balance is sufficient for the first swipe but not the second — say, balance is $15 and amount is $10 — the first call succeeds (balance → $5), and the second call is denied (balance $5 < amount $10). The state after two calls is: balance $5, one log entry. This is also correct — the denial guard works as intended.

The second-call test confirms there is no hidden "already swiped" state that would prevent a legitimate second purchase. A meal-plan card should absolutely be usable multiple times per day.

Question 3

In swipe_card, identify every program artifact. For each one, explain what it does and why it has no problem-level counterpart.

Answer 
def swipe_card(account, amount):
    if amount > account["balance"]:
        print(f"Denied: insufficient balance (${account['balance']:.2f})")
        return                  # artifact 1
    new_balance = account["balance"] - amount   # artifact 2
    account["balance"] = new_balance
    account["log"].append({
        "type": "swipe",
        "amount": amount,
        "balance_after": new_balance
    })
  • return (early return after denial): a control-flow artifact. At the problem level, the event simply "does not happen" — the card is declined and nothing changes. Python needs an explicit instruction to stop executing the function; the problem world has no equivalent concept of a "return statement."
  • new_balance (intermediate variable): a computational artifact. It holds the result of the subtraction so it can be used in two places: updating the balance field and recording it in the log. At the problem level, "the new balance" is not a separate thing — it is simply what the balance becomes. The variable exists to avoid computing the subtraction twice.

Both artifacts are part of the program state while the function executes — the computer tracks them. Neither represents anything in the real world of meal-plan accounts.

Question 4

The vending machine's insert_coin transition: what happens to the state if an unrecognized denomination is inserted? Write the complete transition including that case and a defensive else.

Answer

An unrecognized denomination should be rejected — the coin is not accepted, the credit does not change, and the user is notified. The coin should notionally be returned (though in this simulation, "returning" it means simply not adding it to credit).

VALID_COINS = {0.05, 0.10, 0.25, 1.00}

def insert_coin(machine, denomination):
    if denomination not in VALID_COINS:
        print(f"Unrecognized denomination: ${denomination:.2f}. Coin returned.")
        return   # state unchanged
    machine["credit"] += denomination
    # Defensive else not needed here — the two branches are exhaustive:
    # either the denomination is valid or it isn't.

A defensive else is not necessary in this particular function because the two branches (in VALID_COINS / not in VALID_COINS) are genuinely exhaustive — there is no third possibility. The defensive else pattern is appropriate when a series of if/elif branches covers a finite set of known values and a new value appearing would indicate a programming error:

def handle_account_status(account):
    if account["status"] == "active":
        process_transaction(account)
    elif account["status"] == "suspended":
        print("Account suspended. Contact dining services.")
    else:
        print(f"FATAL ERROR: unknown account status '{account['status']}': 501")
        exit()
Question 5

Why is "a denied transition changes nothing" a design decision worth stating explicitly, rather than something that follows automatically from the code?

Answer

It does not follow automatically from the code — it must be deliberately implemented. A careless implementation of a denial might change some state and not other state. For example, a naive swipe_card might decrement a "attempts" counter even on a denial, or add a "failed swipe" entry to the log before checking the balance. Both would be state changes on a denial.

Stating "a denied transition changes nothing" forces you to check every denial path and verify that no state mutation has occurred before the return. It also communicates intent to anyone reading the code — including a future version of yourself or an AI you are directing. Without the explicit statement, a reader cannot tell whether partial state changes on denial are intentional or accidental.

Finally, it is an invariant of the transition's behavior: "after a denial, the state is identical to the state before the call." That invariant can be tested — call a transition with inputs you know will be denied, and verify that the state dict is unchanged. Stating it explicitly makes it testable.

Section 4 — Invariants

Question 1

For the gradebook: write three domain invariants and two structural invariants in plain English. For each, say whether you would enforce it structurally or with a logic check in check_invariants.

Answer

Domain invariants:

  • "Every score is between 0 and 100 inclusive." — logic check; the range cannot be enforced by the data structure.
  • "A student cannot have a score recorded before they are enrolled." — logic check; requires cross-referencing the scores dict against the roster.
  • "A score list is never empty for a student who has taken at least one quiz." — logic check; the structure allows empty lists.

Structural invariants:

  • "Every student in the scores dict also exists in the roster dict." — logic check; requires verifying referential integrity between two structures.
  • "The scores dict maps student names (strings) to lists (not to individual numbers)." — this can be partially enforced structurally by always constructing entries as scores[name] = [] and using append, but type verification still requires a logic check if loading from a file.
def check_invariants(gradebook):
    for student, score_list in gradebook["scores"].items():
        if student not in gradebook["roster"]:
            print(f"INVARIANT VIOLATED: {student} has scores but is not enrolled")
            exit()
        if not isinstance(score_list, list):
            print(f"INVARIANT VIOLATED: scores for {student} is not a list")
            exit()
        for score in score_list:
            if not (0 <= score <= 100):
                print(f"INVARIANT VIOLATED: score {score} for {student} out of range")
                exit()
Question 2

check_invariants passes, one transition runs, then it fails. What do you now know? What still needs to be determined?

Answer

What you now know: the state was valid before the transition ran, and it is invalid after. The transition that ran between the two checks is responsible for the violation — it introduced the invalid condition. You do not need to search the rest of the code. The bug is in that transition.

What still needs to be determined: exactly which line within the transition caused the violation, and why. The failing invariant check tells you which rule was broken (e.g., "balance is negative") but not the line of code that broke it. You need to inspect the transition itself — look at the guard conditions, the arithmetic, the order of operations. It is possible the guard is missing, incorrect, or applied in the wrong order.

This is the power of the checkpoint discipline: it converts a question of "where in the entire codebase is the bug?" into "where in this one function is the bug?" — a much smaller search space.

Question 4

The library checkout system uses a dict mapping book ID to patron ID. What invariant does that structure enforce automatically, without any code? What invariant does it not enforce — requiring a logic check instead?

Answer

Enforced automatically: "a book can be checked out to at most one patron at a time." A dict cannot have two entries with the same key. Since the key is the book ID, each book ID maps to exactly one patron ID. The structure makes it physically impossible to record the same book as checked out to two different patrons simultaneously.

Not enforced — requires a logic check: "every patron ID recorded in the checkout dict corresponds to a real patron in the patron registry." The dict can hold any string as a value, including a patron ID that was deleted, misspelled, or never existed. The referential integrity between the checkout record and the patron registry must be verified explicitly:

def check_invariants(library):
    for book_id, patron_id in library["checkout"].items():
        if patron_id not in library["patrons"]:
            print(f"INVARIANT VIOLATED: checkout references unknown patron {patron_id}")
            exit()
        if book_id not in library["catalog"]:
            print(f"INVARIANT VIOLATED: checkout references unknown book {book_id}")
            exit()
Question 5

When should you use a defensive else with FATAL ERROR and exit() rather than a guard or an invariant check? Give an example of each and explain the difference.

Answer

Use a defensive else when a series of branches covers every value you believe is possible, and reaching the else branch would mean your understanding of the state space is wrong. It is not handling a user error or checking a rule — it is acknowledging that something has happened that your design said could never happen.

Example of each:

Guard: a user enters a transaction type at the menu. They type "withdrawal" when only "deposit" and "swipe" are valid options. An if guard prints "invalid option" and loops back to the menu. This is a normal, expected input error.

Invariant check: after calling swipe_card, the balance is negative. check_invariants catches this and prints "INVARIANT VIOLATED: balance is negative." This is a code bug — the guard should have prevented this.

Defensive else: inside a function that processes an account status, after handling "active" and "suspended", the else branch fires with "FATAL ERROR: unexpected account status 'premium': 601." The status "premium" does not exist in the design. Someone added a new status value elsewhere in the code without updating this function. The defensive else catches the omission immediately rather than letting the function silently ignore the new status.

The difference: guards and invariant checks operate on conditions the design anticipates. The defensive else fires on conditions the design said were impossible — it is a diagnostic for incomplete state space analysis, not a user-facing error handler.

Question 2

The prompt says "assume amount has already been validated." What would change in the code if that sentence were removed — and at what step of the three-step workflow should that validation decision have been made?

Answer

What changes in the code: without that sentence, the AI will guess. It might add validation inside swipe_card itself — checking that amount is a positive number, wrapping the function in a try/except for type errors, or adding an if amount <= 0 guard. This is not necessarily wrong code, but it is not the design you specified. The validation pattern — validate at the boundary, trust inside — gets violated, and the function's body becomes cluttered with checks that belong elsewhere.

Alternatively, the AI might omit validation entirely and produce a clean function that silently breaks if a negative amount is passed. Both outcomes are worse than the explicitly specified version.

At what step: the decision that "amount is validated before this function is called" is made at Step 1 — the problem-level ISTI spec, specifically in the Inputs section. The spec should say: "INPUT: the cost of the meal being purchased (a positive float). Validated at the boundary before this function is called." The pseudocode and prompt then flow from that decision; they do not make it.

Question 3

The pseudocode says "check whether amount exceeds balance first." Which ISTI concept does that ordering enforce, and what would go wrong if the subtraction happened before the check?

Answer

Which ISTI concept: this ordering enforces the Invariants concept — specifically the domain invariant "balance is never negative." By checking the guard before modifying anything, we ensure that a denied transition leaves the state completely unchanged. This is the "denied transitions change nothing" principle from Section 3, and it is what makes the invariant hold after every transition.

What would go wrong if the subtraction came first:

# Wrong order:
account["balance"] -= amount    # balance may go negative
if account["balance"] < 0:      # now we check... too late
    account["balance"] += amount  # try to undo it
    print("Denied.")
    return

This approach has two problems. First, there is a window — however brief — where the balance is negative. If anything else reads the account state between those two lines (in a more complex system), it sees an invalid state. Second, the "undo" logic adds complexity and creates a new class of bug: what if the undo itself is wrong? The check-before-modify pattern eliminates both problems by never entering an invalid state in the first place.

Question 4

When the AI asks "is a zero-balance swipe a success or a denial?", which of Workbook 1's three legitimate AI roles is it playing? Why is it asking instead of deciding?

Answer

Which role: the AI is playing the role of interrogator — surfacing an unspecified case in your design and asking you to resolve it. This is distinct from the executor role (writing code you have designed) and the assistant role (helping you research or understand something).

Why asking instead of deciding: whether a zero-balance swipe succeeds is a domain question, not a technical one. It depends on the rules of this particular meal plan — does the school allow students to spend their last dollar, or is there a small reserve kept? The AI has no way to know. If it guesses and implements a denial, it may have made a product decision that contradicts what dining services actually wants. If it guesses and allows it, same problem.

More fundamentally: the AI deciding would mean the design belongs to the AI. The student specified a system; the student should decide its rules. The AI asking keeps the design decision — and the learning — with the student. A student who has to answer "yes, a swipe for exactly the balance is a success, the account goes to zero" has actually thought about the problem. A student who copies code that handles this case without knowing why has learned nothing.
