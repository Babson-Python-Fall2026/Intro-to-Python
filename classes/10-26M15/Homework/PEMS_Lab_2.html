Get Your Hands Dirty with the Data

Before you write code to transform data, understand the data you actually have. A program that runs without errors can still produce incorrect results. Good programmers investigate the shape of their data (nested dictionaries and lists, fields, types, indexing) and its quality (missing observations, missing keys, ordering, alignment, duplicates, and unexpected values) rather than assuming the source matches its documentation.

Write small utility programs to investigate

Opening a JSON file and looking at a handful of records is a useful beginning, but not enough. Write short exploratory scripts or functions that count, summarize, compare, and test the datasets. These utilities support your investigation; they are not part of the final portfolio application. Do not simply print thousands of records.

  • Discover the nesting: what does json.load() return, which keys are available, and where do lists and dictionaries appear?
  • Count observations by ticker, identify earliest and latest dates, and test whether dates are sorted, aligned across tickers, duplicated, or missing.
  • Check whether every record has the fields you expect and whether values have the expected data types.
  • Locate dividend and split events, inspect unusual values, and compare related events across source files when appropriate.

Turn expectations into checks

Before relying on an assumption, ask: What do I expect to be true, and what small program could prove or disprove it? For example, you may expect 100 observations for each of 100 tickers, all aligned to the same dates. Test those conditions across the entire dataset, not just the first two securities.

A missing trading day for one ticker can shift every subsequent list-index lookup. The code might continue running while assigning a stock price to the wrong date—often more dangerous than an immediate exception.

Missing does not always mean zero

Distinguish between a missing field, a field containing None, a value of 0, a missing time-series observation, and a value that looks incorrect. These situations do not necessarily mean the same thing. A corporate-action record without a Stock Splits field may describe only a dividend; a missing EOD closing price could prevent the system from valuing a holding. Do not substitute zero without understanding the meaning.

Let the investigation influence your design

Exploration should sometimes confirm your expectations and sometimes challenge them. Either outcome is useful. Use what you discover to decide how to structure market_data, handle absent fields, and validate the finished transformation.

Document evidence, not assumptions. Include a concise Data Exploration Notes section showing which utility checks you wrote, what you tested, what you found, and how your findings affected your code. Include a few representative results; do not submit pages of raw output. A check that finds no problems is still valuable if it thoroughly verifies the assumption.

Complete the unfinished portion of load_data.py. The output is a dictionary indexed by integer trading day (0 through 99). Each day contains its calendar date and a dictionary record for each ticker. Do not repeat the date and ticker in each individual security record.

                "split_in": 1, "split_out": 1},
        # ... remaining tickers

    1: {
        "date": "2025-08-18",
        # ... ticker records for this trading day
    },
    # ... trading days 2 through 99

Example data illustrates the structure. Read actual values from the source files.

  1. Create all 100 trading days × 100 tickers.
  2. Use the EOD Close for price; default dividends to zero and split numerator/denominator to one.
  3. Match corporate actions to the calendar date; incorporate dividends and splits on that date. Use split_out / split_in for new shares per old share.
  4. Retain the provided loader's other responsibilities and return values.

Implementation hints (not a finished solution)

Start small. Develop with range(5) and tickers[:5], inspect your nested structure, and then expand it. You can use pp() on small samples.
Build outside to inside. Loop over trading days, create a dictionary for the date, then loop through tickers and attach a small record for each security. Store the completed day under its index.
Start with defaults. Most day/ticker combinations have no corporate action. Set normal values first, then override them only when an action occurs on the matching date.
Compare comparable dates. The supplied Date strings can be compared using their [:10] calendar-date portion. An early break in an action search requires chronological sorting.
Check the split ratio. Decimal(str(split_factor)).as_integer_ratio() may help turn a decimal factor into an integer ratio. Confirm which output should be split_out and which split_in, and consider whether provider rounding affects the intended ratio.

Part D — Implement client-management actions 30 points

Implement two client-management actions, plus a reusable save helper. Delete Client is not part of this capstone. Clients are stored as a list of dictionaries; their positions in the list identify them during a session. Each action receives state and modifies the shared objects in place. No separate client ID is generated. The save_pems(state) helper is supplied; students are responsible for calling it, not writing it.

1. create_client(state) — 10 points

  1. Prompt for name, email, phone, and starting cash; validate inputs as specified in the starter code.
  2. Construct a new client dictionary with name, email, phone, and transactions (a list).
  3. Create the initial cash-only CONTRIBUTION transaction: trans_id, trd_day, ticker ($$$$), trn_type, shares, cps (1.0), and total_cost. The quantity is nonnegative; transaction type determines direction.
  4. Append the initial transaction to the new client’s transaction list, then append the completed client to state["clients"]. Call the supplied save_pems(state) helper and remain on Client Management.
Understanding the two append operations (answer immediately after Create Client).

Why do we append the initial cash transaction to client["transactions"] and then append the client to clients? When recording a later transaction for an existing client, why is only client["transactions"].append(transaction) needed? What would happen if clients.append(client) were repeated for an existing client, both in memory and after saving and reloading JSON? Explain; do not implement another transaction-entry action in Lab 2.

2. select_client(state) — 10 points

  1. Display clients with menu numbers starting at 1. Handle an empty list and Enter-to-cancel by returning False.
  2. Reprompt for invalid input. On success set state["client_idx"] = choice - 1 and return True, so the wrapper opens Client Portfolio.
  3. When testing selection, use is not None: the first client has index 0, which is falsy.
  4. Do not save JSON when merely selecting a client: only temporary session state changes.

3. Persistence and shared-reference investigation — 10 points

The instructor supplies save_pems(state) as a working helper. Do not implement or modify it. Call the supplied helper after successful client creation and, in later labs, after successful transactions. The helper saves state["pems"] to labs/#capstone/data/pems.json; it does not change pm_users.json.

Investigate and demonstrate the difference between changing shared objects in memory and persisting changes to disk. Include short tests and explanations of all of the following:

  1. Show that state["clients"] is state["pems"][state["pm"]]["clients"] evaluates to True, and explain what is tests.
  2. Create a client using clients.append(client); verify it appears through state["pems"] without reassigning that dictionary.
  3. Demonstrate that modifying the already-selected client dictionary (for example changing a test copy of its phone field) is visible through state["pems"] without re-appending that client. Do not alter the supplied production data for this demonstration.
  4. Explain why append() alone does not update pems.json. Call the supplied save_pems(state) after creating a client, reload the file, and confirm persistence.
  5. Select a client, verify client_idx changes, and verify this does not modify pems or require saving.
Reference structure. state["pems"] is the in-memory PM dictionary; state["clients"] is an alias for the logged-in PM's client list. The only persisted portfolio file is pems.json. No client deletion, client ID keys, or integer-key JSON conversions are needed.
