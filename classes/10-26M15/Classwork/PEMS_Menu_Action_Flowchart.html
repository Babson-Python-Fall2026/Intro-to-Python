2 · What is state? What is included for convenience?

Our program uses a dictionary named state, but not every entry is independent state. To reason about state, first ask: What information must the system retain to determine its next behavior, given its inputs and the underlying data?

state = {
    "pm": current_pm,
    "pems": pems,
    "clients": pems[current_pm]["clients"],
    "client_idx": None,
    "trd_day": 1,
    "market_data": market_data,
    "security_info": security_info
}

stack = ["client_management"]
ItemRoleWhy it matters
state["pm"]Session stateIdentifies the authenticated portfolio manager.
state["client_idx"]Session stateIdentifies the currently selected client; None means none is selected.
state["trd_day"]Simulation stateTracks which of the 100 simulated trading days is current. The calendar date can be derived from market_data.
stackNavigation stateTracks the current menu and the path back. It is real state even though it lives outside the state dictionary.
state["pems"]Persistent business state (held by reference)Contains PMs, clients, and transaction histories. Transactions are the persistent source of truth for portfolio holdings and cash.
state["clients"]Convenience referenceAn alias for state["pems"][state["pm"]]["clients"]. Makes action code shorter, but adds no new information.
state["market_data"]Reference dataProvides prices, dividends, and splits. Passed through the dictionary for easy access; it is not independently changing session state.
state["security_info"]Reference dataProvides descriptions and classifications of securities; also passed for convenient access.
The key distinction: The name state is a programming convenience, not a definition. Actual state includes session and navigation variables and persistent business information. Reference data and duplicate aliases do not become new independent state merely by appearing in this dictionary.

Minimum sufficient session state

Given the persistent PM records and the reference datasets, we can identify the essential session and navigation information with:

session_state = {"pm": current_pm, "client_idx": None, "trd_day": 1}
stack = ["client_management"]

# Both of these can be derived rather than stored independently:
clients = pems[session_state["pm"]]["clients"]
trade_date = market_data[session_state["trd_day"]]["date"]

We still choose to pass pms, clients, market_data, and security_info in the larger state dictionary so every action can accept the simple interface action(state). This avoids long parameter lists; it does not require storing copies of those datasets.

Mutability and the source of truth

state["clients"] is state["pems"][state["pm"]]["clients"]  # True

# Modifying the existing dictionary updates the same client data:
state["clients"].append({"name": "Bob Smith", "email": "", "phone": "", "transactions": []})

# But rebinding the alias breaks that connection:
# state["clients"] = []     # Avoid: new, separate list

Adding a client or appending a transaction changes persistent business state in memory; the relevant action then calls save_pems(state) to persist it. Holdings and cash balances are reconstructed from transactions plus applicable corporate actions, rather than stored as competing sources of truth. The save_pems(state) helper is supplied to students; they call it rather than implement it.

Discussion: ISTI — Inputs, State, Transitions, Invariants

Inputs: choices, trade instructions, and external market events. State: PM, selected client, trade day, menu stack, and persistent transactions. Transitions: select client, buy/sell, advance day, push/pop a menu. Invariants: a selected client belongs to the logged-in PM; PM identities match across credential and portfolio files; transactions cannot sell more shares than are available (assuming no short sales).

Think: If we remove clients from the dictionary, what information is lost? If we remove trd_day, how would the program know which price to use? Why can two accounts with identical holdings and cash still have different cost bases?

4 · How one menu choice is processed

option = menu["options"][int(choice) - 1]

if option["action"] is not None:
    if option["action"](state) is False:
        continue                 # Stay on current menu

if option["next_menu"] is not None:
    stack.append(option["next_menu"])
Critical distinction: Pressing Enter at the stack menu prompt pops the stack. Pressing Enter inside select_client() should return False, which skips navigation and leaves the current stack unchanged.

5 · What changes when an action runs?

Session state

state["client_idx"] changes on client selection; state["trd_day"] changes when advancing trading days. state["clients"] references the current PM’s clients.

Persistent records

Create client and successful buy, sell, contribution, or withdrawal actions should save pems.json via save_pems(state). Dividends and splits are derived from market data and handled under the corporate-action processing rules; they are not user-entered transactions. The saving helper is instructor-supplied.

The menu stack is navigation state, not portfolio state. menus.json supplies action names and next-menu names. The loader maps action-name strings to callable Python functions before the menu loop starts.

6 · In-memory mutation versus saving

These operations change the same Python objects already reachable through state["pems"]:

assert state["clients"] is state["pems"][state["pm"]]["clients"]

# New client
state["clients"].append(client)

# Transaction for an existing client
client = state["clients"][state["client_idx"]]
client["transactions"].append(transaction)

# Save only after modifying persistent records
save_pems(state)

Selection is different: setting state["client_idx"] changes temporary session state, so it does not require saving. A client with index 0 is valid: use is not None when checking selection.

Capstone rule: No Delete Client option. Clients are held in a list and are not removed or reordered; all transaction quantities are nonnegative, with direction determined by trn_type.
